# 文件上传到向量持久化本地 — 系统分析文档

> 版本：v1.0  
> 日期：2026-08-07  
> 项目：ai-assistant（Spring Boot 3.4 + Spring AI 1.1）

---

## 1. 系统概述

本系统实现了一条从**文件上传**到**向量化本地持久化**的完整数据管道。用户上传 PDF 文件后，系统自动完成「文件落盘 → 元数据入库 → PDF 文本提取 → 文本清洗 → 分层切片 → 向量化 → 向量存储 → 磁盘持久化」全流程，并通过异步任务机制保证接口响应速度。

### 1.1 技术栈

| 层次 | 技术选型 | 版本 | 说明 |
|------|---------|------|------|
| 框架 | Spring Boot | 3.4.4 | Java 21 |
| AI 能力 | Spring AI | 1.1.2 | 统一模型抽象 |
| 聊天模型 | DeepSeek API | deepseek-v4-flash | 云端对话 |
| Embedding 模型 | Ollama + bge-m3 | 本地 1024 维 | 本地向量化 |
| 向量存储 | Spring AI SimpleVectorStore | 内置 | 内存 + 本地 JSON 持久化 |
| ORM | MyBatis-Plus | 3.5.7 | 数据库操作 |
| 数据库 | MySQL | 8.x | 文档元数据 |
| PDF 解析 | Apache PDFBox | 3.0.5 | PDF → 文本 |
| Token 估算 | jtokkit (CL100K_BASE) | — | 切片 token 计数 |
| 异步任务 | Spring @Async + ThreadPoolTaskExecutor | — | 后台文档处理 |

### 1.2 核心设计目标

1. **接口快速响应**：上传接口同步仅做文件落盘 + 元数据入库，向量化等耗时操作异步执行。
2. **本地优先**：Embedding 走本地 Ollama（bge-m3），向量存储走内存 + 本地文件，无需部署外部向量数据库。
3. **可扩展性**：通过 `VectorStoreService` 接口抽象，当前使用 `SimpleVectorStoreService`，未来可无缝切换到 Milvus / PGVector 等（代码中已保留 Milvus 实现骨架）。
4. **数据可恢复**：向量数据按文档粒度序列化为 JSON 文件落盘，应用重启时自动加载到内存。
5. **质量保障**：多层文本清洗 + 分层切片策略，保障向量化质量和检索效果。

## 3. 模块详细分析

### 3.1 文件上传层

#### 3.1.1 DocumentController

- **位置**：`controller/DocumentController.java`
- **接口**：
  - `POST /document/upload` — 单文件上传
  - `POST /document/batchUpLoad` — 多文件上传（串行循环处理）
- **请求**：`multipart/form-data`，参数名 `file` / `files`
- **响应**：`Result<DocumentUploadResult>`，包含 `documentId`、`fileName`、`fileSize`、`fileUrl`、`processStatus`

#### 3.1.2 DocumentUploadServiceImpl

- **位置**：`service/impl/DocumentUploadServiceImpl.java`
- **核心逻辑**：
  1. **空文件校验**：文件为空抛出 `BusinessException`
  2. **目录组织**：按当天日期 `yyyy-MM-dd` 建子目录（`./upload/2026-08-07/`）
  3. **文件命名**：`当前时间戳 + 原始扩展名`（如 `1723012345678.pdf`）
  4. **落盘方式**：`file.transferTo(dest)`，使用 `getCanonicalFile()` 确保绝对路径
  5. **元数据入库**：写入 `document_info` 表，状态 `pending`
  6. **异步触发**：调用 `documentProcessService.processDocument(documentId)`
- **存储字段**：
  | 字段 | 说明 |
  |------|------|
  | `fileName` | 存储文件名（时间戳.扩展名） |
  | `originFileName` | 原始上传文件名 |
  | `fileType` | 文件扩展名（含点） |
  | `fileSize` | 文件大小（字节） |
  | `fileUrl` | 访问 URL（`/upload/日期/文件名`） |
  | `storagePath` | 本地绝对路径 |
  | `storageType` | `local` |
  | `processStatus` | `pending` → `processing` → `completed` / `failed` |

#### 3.1.3 静态资源映射

- **位置**：`common/WebMvcConfig.java`
- 将 `./upload/` 目录映射为 `/upload/**` 可 HTTP 访问的静态资源路径
- 同时配置了全局 CORS（允许所有来源 / 方法 / 头）

### 3.2 文档处理层（异步）

#### 3.2.1 异步线程池

- **位置**：`common/AsyncConfig.java`
- **Bean 名称**：`documentProcessExecutor`
- **配置**：
  - 核心线程数：2
  - 最大线程数：4
  - 队列容量：100
  - 拒绝策略：`CallerRunsPolicy`（队列满时由调用线程执行，避免丢失任务）
  - 线程名前缀：`doc-process-`

#### 3.2.2 DocumentProcessServiceImpl

- **位置**：`service/impl/DocumentProcessServiceImpl.java`
- **执行模式**：`@Async("documentProcessExecutor")`
- **状态机**：
  ```
  pending ──开始处理──▶ processing ──成功──▶ completed
                          │
                          └────失败────▶ failed（记录错误信息）
  ```
- **流程步骤**：
  1. 根据 `documentId` 查询 `document_info` 记录
  2. 非 PDF 文件直接标记为 `completed` 并返回
  3. 校验文件是否存在
  4. 更新状态为 `processing`
  5. 使用 PDFBox 提取文本（`setSortByPosition(true)` 保证阅读顺序）
  6. 文本清洗 → `textCleanService.clean(rawText)`
  7. 文本切片 → `textChunkService.chunk(cleanedText, docId, docName)`
  8. 向量化 + 存储 → `embeddingService.embedAndStore(chunks)`
  9. 更新状态为 `completed`
  10. 异常时捕获并标记为 `failed`，错误信息截断到 990 字符

### 3.3 文本清洗层

#### 3.3.1 TextCleanServiceImpl

- **位置**：`service/impl/TextCleanServiceImpl.java`
- **清洗流程**（5 步）：

| 步骤 | 操作 | 关键实现 |
|------|------|---------|
| 1 | 分页 + 页眉页脚识别 | 按 `\f` 分页；统计每页前 2 行 / 后 2 行的短行出现频率，≥50% 视为页眉/页脚 |
| 2 | 去页码 | 5 种正则模式：纯数字、第N页、中文数字页、带装饰符页码、Page N of N |
| 3 | 单行清洗 | 全角空格 `　`、Tab `\t`、不间断空格 ` ` → 普通空格；多空格合并 |
| 4 | 去相邻重复行 | 标题跨行重复时去重，空行打断重复判定 |
| 5 | 段落合并 + 空行压缩 | 按句末标点（`。！？.!?；;：:`）判断段尾，否则与下一行合并；连续空行压到 1 个 |

- **关键参数**：
  - `HEADER_FOOTER_MAX_LEN = 100`（页眉页脚候选行最大长度）
  - `HEADER_FOOTER_THRESHOLD = 0.5`（出现频率阈值）

### 3.4 文本切片层

#### 3.4.1 TextChunkServiceImpl

- **位置**：`service/impl/TextChunkServiceImpl.java`
- **Token 编码**：jtokkit 库，`EncodingType.CL100K_BASE`（GPT-4 同款编码）
- **分层切分策略**（5 层）：

```
原始清洗文本
    │
    ▼ 第 1 层：按章节切分
    │  识别规则（任一匹配即为章节标题）：
    │  ├─ 第X章/节/篇/回/部/卷
    │  ├─ Markdown 标题 (# / ##)
    │  ├─ 数字编号标题 (1. / 1.2 / 1、)
    │  └─ 中文数字+顿号 (一、二、)
    │  标题行长度限制：≤ 80 字符
    │
    ▼ 第 2 层：按段落切分
    │  按空行（\n\s*\n）切分
    │  过短段落（< 20 字符）并入上一段
    │
    ▼ 第 3 层：按 Token 长度切分
    │  目标 chunk size: 500 tokens
    │  优先在句末标点处断开（。！？.!?；;）
    │  找不到则硬切
    │
    ▼ 第 4 层：Overlap 重叠
    │  重叠长度: 50 tokens
    │  同一章节内相邻 chunk 首尾重叠
    │
    ▼ 第 5 层：Metadata 注入
       每个 TextChunk 携带：
       ├─ content（文本内容）
       ├─ chunkIndex（全局序号）
       ├─ totalChunks（总数）
       ├─ chapterTitle / chapterIndex
       ├─ documentId / documentName
       └─ tokenCount（本 chunk token 数）
```

### 3.5 向量化层

#### 3.5.1 EmbeddingServiceImpl

- **位置**：`service/impl/EmbeddingServiceImpl.java`
- **模型**：通过 Spring AI `EmbeddingModel` 抽象，当前实现为 Ollama `bge-m3`（1024 维）
- **批量策略**：
  - 配置项：`ai.embedding.batch-size`（默认 16）
  - 将 chunks 列表按 batch-size 分批
  - 调用 `embeddingModel.embed(List<String>)` 批量向量化
  - 每 5 批打印一次进度日志
- **核心方法**：
  - `embed(String text)` — 单文本向量化
  - `embedChunks(List<TextChunk>)` — 批量向量化，返回 `List<EmbeddedChunk>`
  - `embedAndStore(List<TextChunk>)` — 向量化 + 存入向量库（**对外主入口**）
- **启动日志**：打印实现类、向量维度、批大小、存储实现等配置信息

### 3.6 向量存储层

#### 3.6.1 SimpleVectorStoreService

- **位置**：`service/impl/SimpleVectorStoreService.java`
- **继承关系**：`extends SimpleVectorStore implements VectorStoreService`
- **标记**：`@Primary`（优先注入）
- **内存结构**：
  - `store`（继承自 `SimpleVectorStore`）：`ConcurrentHashMap<String, SimpleVectorStoreContent>`
    - Key: `doc_{documentId}_chunk_{chunkIndex}`
    - Value: `SimpleVectorStoreContent`（id + content + metadata + embedding）
  - `docToChunkIds`：`Map<Long, CopyOnWriteArrayList<String>>`
    - 维护 `documentId → chunkId 列表` 的映射
    - 用于支持按文档删除（SimpleVectorStore 原生只支持按 ID 删除）
- **核心方法**：
  - `saveAll(List<EmbeddedChunk>)` — 批量写入，直接操作 `store`（绕过二次 embedding）
  - `deleteByDocumentId(Long)` — 按文档 ID 删除所有 chunk
- **启动初始化**（`@PostConstruct`）：
  1. 打印配置日志
  2. 调用 `loadVectorsFromDisk()` 从磁盘加载已有向量
  3. 重建 `docToChunkIds` 映射
- **Metadata 字段**：
  | 字段 | 类型 | 说明 |
  |------|------|------|
  | `chunkId` | String | 唯一标识 `doc_{id}_chunk_{idx}` |
  | `documentId` | Long | 关联文档主键 |
  | `chunkIndex` | Integer | 全局 chunk 序号 |
  | `totalChunks` | Integer | 文档总 chunk 数 |
  | `chapterIndex` | Integer | 章节序号 |
  | `chapterTitle` | String | 章节标题 |
  | `documentName` | String | 原始文件名 |
  | `tokenCount` | Integer | token 数 |

#### 3.6.2 VectorStorePersistenceManager

- **位置**：`service/impl/VectorStorePersistenceManager.java`
- **持久化目录**：`ai.vector-store.persistence-path`（默认 `./vector-store`）
- **文件格式**：每个文档一个 JSON 文件 `doc_{documentId}.json`
- **文件内容**：`List<SimpleVectorStoreContent>`（Spring AI 类自带 Jackson 注解）

**写入流程**：
```
saveDocumentVectors(documentId, contents)
    │
    ├─ 校验: persistenceEnabled && documentId != null
    │
    ├─ 加锁: docLocks.computeIfAbsent(docId, ReentrantLock)  // 按文档粒度锁
    │
    ├─ 步骤 1: 写临时文件 doc_{id}.json.tmp
    │          objectMapper.writeValue(tmp, contents)
    │
    ├─ 步骤 2: 原子重命名 tmp.renameTo(target)
    │          失败 fallback 到直接覆盖写入 + 删除 tmp
    │
    └─ 释放锁
```

**启动加载流程**：
```
loadAll(validator)
    │
    ├─ 遍历目录，匹配 doc_*.json
    │
    ├─ 逐个文件反序列化为 List<SimpleVectorStoreContent>
    │
    ├─ 从 metadata 提取 documentId
    │
    ├─ 调用 validator.isValid(docId)
    │   (检查 document_info 表中是否存在且未逻辑删除)
    │   ├─ 有效 → 加入结果 map
    │   └─ 无效 → 自动删除脏文件
    │
    ├─ 损坏文件 → 跳过 + 日志（不影响启动）
    │
    └─ 返回 chunkId → content 的完整 map
```

- **并发安全**：每个 documentId 对应一个 `ReentrantLock`，避免同一文档并发写入错乱
- **容错机制**：
  - 损坏文件跳过，不影响其他文档和启动
  - 数据库中已删除的文档对应的向量文件自动清理
  - renameTo 跨文件系统失败时有 fallback 策略

## 4. 关键设计决策

### 4.1 同步上传 + 异步处理

- **决策**：上传接口只做文件落盘和元数据入库，向量化等耗时操作通过 `@Async` 异步执行
- **理由**：
  - 大文件 PDF 解析 + 向量化可能耗时数十秒到数分钟
  - 同步等待会导致 HTTP 超时，用户体验差
  - 通过 `processStatus` 字段让前端可轮询处理进度
- **权衡**：需要前端配合轮询或 WebSocket 推送状态（当前仅提供状态字段）

### 4.2 本地 Ollama + bge-m3 做 Embedding

- **决策**：Embedding 不调用云端 API，使用本地 Ollama 部署的 bge-m3 模型
- **理由**：
  - 数据隐私：文档内容不出本地
  - 成本：无 API 调用费用
  - 中文效果：bge-m3 多语言模型，中文效果优秀
  - 维度：1024 维，在效果和存储成本间取得平衡
- **依赖**：应用启动前必须安装 Ollama 并 pull bge-m3 模型
- **约束**：启动时若 Ollama 不可用，首次向量化调用会报错

### 4.3 SimpleVectorStore + 本地 JSON 持久化

- **决策**：暂不使用 Milvus 等专业向量数据库，使用 Spring AI 内置 SimpleVectorStore + 自研持久化管理器
- **理由**：
  - 开发调试便捷，零外部依赖
  - 数据量小时性能足够（全内存 + 余弦相似度）
  - 按文档粒度 JSON 文件，便于调试和迁移
  - 抽象了 `VectorStoreService` 接口，切换成本低
- **Milvus 升级路径**：代码中已保留 `MilvusConfig` / `MilvusProperties` / `MilvusVectorStoreService` 骨架，pom.xml 中也有注释掉的依赖，后续取消注释并配置即可切换

### 4.4 分层切片策略

- **决策**：采用「章节 → 段落 → Token 长度 → Overlap → Metadata」五层切分
- **理由**：
  - 纯按字符/token 硬切会破坏语义完整性
  - 章节级切分保留文档结构信息
  - 段落级切分尊重自然语义边界
  - Token 级切分确保 chunk 大小在模型处理范围内
  - Overlap 避免跨 chunk 语义断裂
  - Metadata 便于后续过滤检索和结果溯源

### 4.5 按文档粒度持久化

- **决策**：每个文档对应一个 `doc_{id}.json` 文件，而非全部向量存一个文件
- **理由**：
  - 按文档删除只需删一个文件，O(1) 操作
  - 单文档更新/重算不影响其他文档
  - 启动加载时可并行处理（当前为串行，可优化）
  - 损坏影响范围小（单个文件损坏不影响全局）
  - 便于增量备份

## 7. 异常处理与容错

| 场景 | 处理方式 |
|------|---------|
| 上传文件为空 | 抛出 `BusinessException`，返回错误提示 |
| 创建上传目录失败 | 抛出 `BusinessException` |
| 文档不存在（异步） | 日志 warn，静默返回 |
| 非 PDF 文件 | 直接标记 completed（无内容） |
| PDF 解析失败 | 标记 failed，记录错误信息 |
| 文本清洗 / 切片失败 | 由外层 try-catch 捕获，标记 failed |
| Embedding 调用失败 | 由外层 try-catch 捕获，标记 failed |
| 向量持久化写入失败 | 日志 error，内存数据仍有效（不影响查询） |
| 向量文件损坏（启动时） | 跳过该文件，日志记录，不影响启动 |
| 向量文件对应文档已删除 | 自动清理脏文件 |
| 线程池队列满 | CallerRunsPolicy，由调用线程执行 |

## 8. 已知约束与优化方向

### 8.1 当前约束

1. **仅支持 PDF**：非 PDF 文件直接跳过解析，不支持 Word / Excel / PPT / TXT 等格式
2. **向量检索未暴露接口**：`VectorStoreService` 有存储能力但无查询 API（RAG 检索模块待接入）
3. **无处理进度回调**：只有 4 种状态（pending/processing/completed/failed），无百分比进度
4. **串行向量化**：单文档内 chunk 分批串行调用 Ollama，未并发
5. **启动加载串行**：向量文件逐个加载，大数量下启动慢
6. **全内存存储**：SimpleVectorStore 全部数据在内存，文档量大时占用内存高
7. **无重复上传检测**：相同文件多次上传会产生多条记录和多份向量

### 8.2 优化建议

| 优先级 | 优化点 | 方案 |
|--------|--------|------|
| 高 | 扩展文件格式支持 | 接入 Apache POI（Office）、Tika（多格式） |
| 高 | 暴露向量检索 API | 新增 `VectorQueryController`，封装 similaritySearch |
| 中 | 处理进度细化 | 增加 `processProgress` 字段（0-100），分步更新 |
| 中 | 并发向量化 | 单文档内批次并行调用，或多文档并发处理 |
| 中 | 重复文件检测 | 文件 MD5 去重，相同文件复用已有向量 |
| 低 | 升级到 Milvus | 取消 Milvus 相关注释，配置连接参数即可 |
| 低 | 向量文件压缩 | 使用二进制格式（如 .npy + protobuf）减少磁盘占用 |
