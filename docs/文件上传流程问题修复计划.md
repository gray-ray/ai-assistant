# 文件上传流程问题修复计划

## 1. 背景

当前文件上传链路已经具备基础能力：用户通过 `/document/upload` 或 `/document/batchUpLoad` 上传文件，后端完成本地落盘、`document_info` 入库，并异步执行 PDF 解析、文本清洗、切片、Embedding 和向量持久化。

但现有实现更接近“全局文档库”的雏形，距离稳定可用的用户上传 RAG 流程还有几个关键缺口：

- 上传文档未绑定用户、会话或消息，聊天检索默认查全局向量库，存在数据串用风险。
- 任意文件可以落盘，非 PDF 被标记为 `completed`，状态语义不准确。
- 上传目录通过 `/upload/**` 直接暴露，缺少访问鉴权和文件类型安全边界。
- 文件名使用毫秒时间戳，并发上传可能重名覆盖。
- 文件落盘、数据库入库、异步向量写入之间缺少一致性补偿。
- 缺少处理状态查询、失败重试、批量上传逐文件结果和前端上传入口。

本文给出分阶段修复计划，目标是先消除安全和数据隔离风险，再补齐体验与可维护性。

## 2. 总体目标

### 2.1 功能目标

1. 上传文件必须能归属到明确范围：用户、会话、消息或知识库。
2. 聊天检索只能召回当前用户/会话/知识库允许访问的文档。
3. 处理状态可查询，失败原因可展示，必要时可重试。
4. 批量上传可返回每个文件的独立结果。
5. 前端具备完整上传入口和处理进度展示。

### 2.2 安全目标

1. 只允许白名单文件类型进入解析链路。
2. 上传文件不直接裸露为公共静态资源，至少要经过权限校验。
3. 防止文件名冲突、路径逃逸和异常文件污染存储目录。
4. 密钥配置从仓库配置文件迁移到环境变量。

### 2.3 稳定性目标

1. 上传文件落盘和数据库记录之间有失败补偿。
2. 文档处理失败后状态准确，不留下误导性的 `completed`。
3. 向量写入失败时不产生“数据库失败但内存向量可检索”的半成功状态。
4. 提供可测试、可回归的上传处理用例。

## 3. 优先级拆分

| 优先级 | 问题 | 影响 | 目标版本 |
| --- | --- | --- | --- |
| P0 | 文档没有用户/会话隔离，检索默认全局召回 | 数据串用、权限越界 | V1 |
| P0 | 文件类型无严格白名单，上传目录直接公开 | 安全风险、状态误导 | V1 |
| P1 | 文件名可能冲突，上传与入库缺少补偿 | 文件覆盖、孤儿文件、半成功状态 | V2 |
| P1 | 空文本 PDF 被标记为成功，缺少重试/删除 | 用户体验差、检索不可预期 | V2 |
| P2 | 批量上传结果粗糙，前端无上传入口 | 难以定位失败，流程不完整 | V2 |
| P2 | 配置硬编码、密钥明文、测试不足 | 可维护性和运维风险 | V2 |

## 4. 阶段一：安全与隔离修复（P0）

### 4.1 文档归属模型

#### 问题

`document_info` 表中已有 `user_id` 字段，但上传接口未接收这些参数，`DocumentUploadServiceImpl` 入库时也没有写入。聊天检索构造 `VectorSearchRequest` 时只传 `queries`，没有传 `documentIds`，导致所有已向量化文档都可能被召回。

#### 方案

1. 改造上传接口，至少接收：
   - `userId`
   - 可选 `sessionId`
   - 可选 `messageId`
   - 后续知识库化时可扩展 `knowledgeId`

2. 上传前校验：
   - `session.userId == userId`。
   - 当前用户有权限向该会话上传文件。

3. 入库时写入：
   - `document_info.user_id`

4. 向量 metadata 中补充：
   - `userId`
   - `documentId`
   - `documentName`

5. 聊天检索前先查询当前会话可用文档 ID：
   - `select id from document_info where user_id = ? and session_id = ? and process_status = 'completed' and is_deleted = 0`

6. 构造 `VectorSearchRequest` 时传入 `documentIds`。

#### 涉及文件

- `ai-assistant-document/src/main/java/org/grayray/aiassistant/document/controller/DocumentController.java`
- `ai-assistant-document/src/main/java/org/grayray/aiassistant/document/service/DocumentUploadService.java`
- `ai-assistant-document/src/main/java/org/grayray/aiassistant/document/service/impl/DocumentUploadServiceImpl.java`
- `ai-assistant-document/src/main/java/org/grayray/aiassistant/document/entity/DocumentInfo.java`
- `ai-assistant-chat/src/main/java/org/grayray/aiassistant/chat/service/impl/ChatServiceImpl.java`
- `ai-assistant-rag-api/src/main/java/org/grayray/aiassistant/rag/retrieval/VectorSearchRequest.java`
- `ai-assistant-rag-core/src/main/java/org/grayray/aiassistant/rag/retrieval/filter/MetadataFilter.java`
- `ai-assistant-rag-core/src/main/java/org/grayray/aiassistant/rag/service/impl/SimpleVectorStoreService.java`

#### 验收标准

- A 用户上传文档后，B 用户在自己的会话中无法召回该文档内容。
- 同一用户不同会话是否共享文档，要按产品策略明确：
  - 会话私有：只召回当前会话文档。
  - 用户私有：召回当前用户所有可用文档。
  - 知识库模式：召回当前用户已选择知识库文档。
- `VectorSearchRequest.documentIds` 为空时的行为需要明确，建议在聊天场景不允许空范围默认为全局检索。

### 4.2 文件类型白名单与上传安全

#### 问题

当前只根据原始文件名截取扩展名，并在处理阶段跳过非 PDF。这样会导致任意文件被保存到 `upload` 目录，且非 PDF 被标记为 `completed`。

#### 方案

1. 新增上传配置：
   - `ai.upload.base-dir`
   - `ai.upload.url-prefix`
   - `ai.upload.max-file-size`
   - `ai.upload.allowed-extensions`
   - `ai.upload.allowed-content-types`

2. 上传阶段做三层校验：
   - 扩展名白名单：第一阶段只允许 `.pdf`。
   - Content-Type 白名单：`application/pdf`。
   - 文件头校验：PDF 必须以 `%PDF-` 开头。

3. 非支持类型直接返回业务错误，不入库、不落盘。

4. 原始文件名只用于展示，不参与存储路径拼接。

5. 对异常文件名做长度限制和清洗：
   - 去除路径分隔符。
   - 限制 `origin_file_name` 长度不超过表字段。
   - 对空文件名使用默认展示名。

#### 验收标准

- `.exe`、伪装成 `.pdf` 的文本文件、空文件均无法入库。
- 合法 PDF 上传后状态为 `pending`，随后进入异步处理。
- 错误响应能明确提示“不支持的文件类型”或“文件为空”。

### 4.3 上传文件访问控制

#### 问题

`WebMvcConfig` 将本地 `./upload` 映射为 `/upload/**`，任何知道路径的人都可能直接访问原始文件。

#### 方案

第一阶段建议先取消公共静态映射，改为受控下载接口：

- `GET /document/{documentId}/download`

下载前校验：

1. 文档存在且未删除。
2. 当前用户有权访问该文档。
3. 文件实际路径位于配置的上传根目录内。

如果短期仍需保留 `/upload/**`，至少要做到：

- 不在上传结果中返回可直接公网访问的 `fileUrl`。
- 前端展示使用 `documentId`，下载时走鉴权接口。
- 静态映射仅开发环境开启。

#### 验收标准

- 未登录或错误用户无法下载他人文档。
- 构造路径参数无法访问上传目录之外的文件。

## 5. 阶段二：一致性与状态修复（P1）

### 5.1 存储文件名防冲突

#### 问题

当前文件名使用 `System.currentTimeMillis() + extension`，同一毫秒内同扩展名上传可能覆盖。

#### 方案

使用 UUID 或 ULID：

- `yyyy-MM-dd/{uuid}.pdf`

可选增强：

- 文件名中加入 `documentId`，例如 `doc_{documentId}_{uuid}.pdf`。
- 写文件使用不可覆盖语义，避免同名覆盖。

#### 验收标准

- 并发上传 100 个同名 PDF，不产生覆盖。
- 数据库 `file_name` 和磁盘文件一一对应。

### 5.2 上传落盘和入库补偿

#### 问题

当前先落盘再入库。若入库失败，会留下孤儿文件。若异步处理失败，原文件和可能已写入的向量没有统一清理策略。

#### 方案

1. 上传同步阶段：
   - 校验通过。
   - 创建数据库记录，状态为 `pending`。
   - 落盘文件。
   - 更新 `storage_path`、`file_url`。
   - 任一步失败时执行补偿。

2. 补偿策略：
   - DB 记录创建成功但文件保存失败：标记 `failed`，记录 `process_error`。
   - 文件保存成功但 DB 更新失败：删除已保存文件。
   - 异步处理失败：标记 `failed`，删除已写入向量。

3. 对 `DocumentProcessServiceImpl` 中向量写入增加幂等处理：
   - 处理前先删除该 `documentId` 的旧向量。
   - 成功后再标记 `completed`。
   - 失败时确保该文档不可被检索。

#### 验收标准

- 模拟 DB 保存失败，不产生孤儿文件。
- 模拟 embedding 失败，文档状态为 `failed`，检索不到该文档 chunk。
- 重试同一文档不会产生重复向量。

### 5.3 处理状态语义完善

#### 问题

空文本 PDF 或扫描版 PDF 可能没有任何 chunk，但当前仍会标记为 `completed`。

#### 方案

状态枚举建议扩展为：

- `pending`：已接收，等待处理。
- `processing`：正在解析、切片或向量化。
- `completed`：已成功生成可检索 chunk。
- `completed_empty`：处理完成，但未提取到可检索文本。
- `failed`：处理失败。

如果暂时不增加状态枚举，也应在 0 chunk 时标记 `failed`，错误信息为“未提取到可检索文本”。

建议表字段补充：

- `chunk_count`
- `vector_count`
- `processed_at`

#### 验收标准

- 扫描版 PDF 不再显示为普通成功。
- 前端能展示“未提取到文本，请上传可复制文本的 PDF 或等待 OCR 支持”。

### 5.4 状态查询和失败重试

#### 方案

新增接口：

- `GET /document/{documentId}`：查询文档详情。
- `GET /document/{documentId}/status`：轻量查询处理状态。
- `POST /document/{documentId}/retry`：失败后重新处理。
- `DELETE /document/{documentId}`：逻辑删除文档，并删除向量。

状态查询返回：

- `documentId`
- `originFileName`
- `fileSize`
- `processStatus`
- `processError`
- `chunkCount`
- `vectorCount`
- `createTime`
- `processedAt`

#### 验收标准

- 上传接口返回 `documentId` 后，前端可轮询状态直到终态。
- `failed` 文档可重试。
- 删除文档后向量检索不再召回。

## 6. 阶段三：批量上传和前端体验（P2）

### 6.1 批量上传逐文件结果

#### 问题

当前批量接口串行调用单文件上传，空文件被跳过，中途失败会导致整体异常，调用方无法知道哪些成功、哪些失败。

#### 方案

新增批量结果 VO：

- `originFileName`
- `success`
- `documentId`
- `processStatus`
- `errorCode`
- `errorMessage`

接口调整：

- 新增标准路径：`POST /document/batchUpload`
- 保留兼容路径：`POST /document/batchUpLoad`

批量上传中单个文件失败不影响其他文件处理，最终返回每个文件的独立状态。

#### 验收标准

- 3 个文件中 1 个非法，返回 2 个成功、1 个失败。
- 前端能逐条展示成功/失败原因。

### 6.2 前端上传入口

#### 方案

在当前聊天页面补齐文件上传体验：

1. 消息输入区域增加附件按钮。
2. 选择文件后展示待上传列表。
3. 上传时展示进度、文件大小、状态。
4. 上传成功后轮询处理状态。
5. 处理完成后提示“已加入当前会话上下文”。
6. 失败时展示 `processError`。

前端接口建议：

- `uploadDocument(file, userId, sessionId)`
- `getDocumentStatus(documentId)`
- `deleteDocument(documentId)`
- `retryDocument(documentId)`

#### 验收标准

- 用户无需离开聊天页即可上传 PDF。
- 上传完成但处理未完成时，发送问题应提示“文档仍在处理中”或暂不召回该文档。
- 处理失败有可读提示。

## 7. 阶段四：配置、测试与运维完善（P2）

### 7.1 上传配置统一

#### 方案

新增配置类：

- `UploadProperties`

配置示例：

```yaml
ai:
  upload:
    base-dir: ./upload
    url-prefix: /document
    allowed-extensions:
      - .pdf
    allowed-content-types:
      - application/pdf
    public-static-enabled: false
```

替换以下硬编码：

- `DocumentUploadServiceImpl.UPLOAD_DIR`
- `DocumentUploadServiceImpl.URL_PREFIX`
- `WebMvcConfig.UPLOAD_DIR`
- `WebMvcConfig.URL_PREFIX`

### 7.2 密钥配置迁移

#### 问题

`application.yaml` 中存在明文 API Key。

#### 方案

1. 将密钥改为环境变量占位：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
```

2. 更新 README 启动说明。
3. 轮换已暴露的 Key。

### 7.3 测试计划

#### 单元测试

- `DocumentUploadServiceImplTest`
  - 空文件拒绝。
  - 非 PDF 拒绝。
  - 伪 PDF 拒绝。
  - UUID 文件名不冲突。
  - DB 失败时清理文件。

- `DocumentProcessServiceImplTest`
  - 正常 PDF 处理为 `completed`。
  - 空文本 PDF 标记为 `completed_empty` 或 `failed`。
  - embedding 失败标记为 `failed`。

- `MetadataFilterTest`
  - `documentIds` 过滤生效。
  - 空范围策略符合聊天场景预期。

#### 集成测试

- 用户 A 上传文档，用户 B 检索不到。
- 同用户不同会话按产品策略隔离或共享。
- 删除文档后不再召回。
- 重试失败文档不会产生重复向量。

#### 前端测试

- 上传成功状态展示。
- 处理失败状态展示。
- 批量上传部分失败展示。
- 删除附件后状态更新。

## 8. 推荐实施顺序

1. 抽出 `UploadProperties`，统一上传目录和 URL 配置。
2. 上传接口增加 `userId/sessionId`，并写入 `document_info`。
3. 聊天检索前查询当前范围内 `documentIds`，并传入 `VectorSearchRequest`。
4. 增加文件类型白名单和 PDF 文件头校验。
5. 将 `/upload/**` 改为受控下载接口，或至少先在开发环境外关闭静态映射。
6. 文件名改为 UUID/ULID，补齐落盘和入库补偿。
7. 完善处理状态、状态查询、删除和重试接口。
8. 改造批量上传返回结构。
9. 补齐前端上传入口和轮询状态。
10. 补测试，迁移密钥配置，更新 README。

## 9. 版本里程碑

### V1：安全可用版

范围：

- 用户/会话隔离。
- PDF 白名单校验。
- UUID 文件名。
- 状态查询接口。
- 聊天检索按 `documentIds` 限定范围。

完成后系统可以用于受控测试环境。

### V2：稳定体验版

范围：

- 删除和重试接口。
- 批量上传逐文件结果。
- 前端上传入口。
- 空文本 PDF 状态处理。
- 上传补偿和向量幂等。

完成后系统可以用于真实用户试用。

### V3：知识库化版

范围：

- 增加 `knowledge_id`。
- 支持用户选择知识库范围。
- 支持文档列表、文档更新、重新切片。
- 支持 OCR 或更多文档格式。

完成后上传流程从“会话附件”升级为“可管理知识库”。

## 10. 风险与决策点

1. 文档范围策略需要产品确认：
   - 会话私有。
   - 用户私有。
   - 知识库私有。

2. `/upload/**` 是否保留：
   - 开发环境保留方便调试。
   - 生产环境建议关闭，改用鉴权下载接口。

3. 空文本 PDF 的状态：
   - 如果短期不做 OCR，建议使用 `completed_empty`。
   - 如果希望简单处理，先用 `failed` 也可以。

4. 向量存储一致性：
   - SimpleVectorStore 当前是内存加本地文件持久化，适合开发和小规模。
   - 多实例部署前需要切换到 Milvus、PGVector 或其他集中式向量库。

- [ ] 处理失败不会产生可检索向量。
- [ ] 用户不能召回其他用户文档。
- [ ] 会话范围策略符合预期。
- [ ] 文档状态可查询。
- [ ] 失败文档可重试。
- [ ] 删除文档后向量同步删除。
- [ ] 批量上传返回逐文件结果。

- [ ] API Key 已迁移到环境变量并完成轮换。
